<design_decisions>
Planner decisions (discretion, justified):
- PD-1 (where the colour lives): the sim never sees a colour. `laserFired` gains `specKey?: string`, the NPC shooter's
  hull key (the role-name style of PROJECT.md row (g), the same name `shipDestroyed` and `identLocked` use), absent on
  the player's shots. The app maps it to a colour through `TrafficContent.laserColors`, built once from the catalogue,
  and hands the shot layer an optional RGB tuple. The shot layer still stores no entity id. Reason: colour is
  presentation; a world lookup after the step fails for a shooter killed in the same tick.
- PD-2 (what the build accepts): `laserColorExtra` compiles an absent key to null (Oolite's nil, so the weapon colour
  applies) and a string naming one of OOColor's fifteen named colours (`OOColor.m:234-307`) to its float32 RGB, kept
  only when its brightness is at least 0.5, where `brightColorWithDescription` returns it unchanged. Everything else
  fails the build with a ContentError on `laser_color`: an unknown `...Color` name (Oolite would silently fall back), a
  numeric string, an array or a dictionary (`colorFromString` and the dictionary forms, `OOColor.m:140-199`, are not
  ported), and blackColor, darkGrayColor and clearColor (brightness below 0.5, whose HSB rebuild is not ported).
  This is a deliberate narrowing in the style of `fragment_chance`: the vendored data uses named colours only, and a
  pin bump that authors another form must fail loudly instead of drawing a wrong colour.
- PD-3 (render guard): `add` uses the given colour only when it has three finite components in [0, 1]; otherwise it
  uses `LASER_SHOT_COLORS[laserKind]`. The schema already bounds the compiled value; the guard keeps a bad tuple from
  reaching the vertex buffer.
- PD-4 (task shape): one tracer task carries the whole data path (one new record field, one new event field, one map,
  one argument), because each layer's edit is a few lines and the CHANGELOG entry must land in the commit that makes
  the change visible. Splitting it would commit a field with no consumer.
</design_decisions>
