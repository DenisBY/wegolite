## Decisions this plan implements

- **Carried forward (CONTEXT):** statics are hit by porting Oolite's subentity rule; the station only absorbs hits and is never destroyed; Phase 18 supersedes "Statics are neither laser nor ident targets" in the same commit as the rule change (this plan the laser half; 18-06 the ident half, on the same new row).

- **A6 (recorded here):** the station's energy is not decremented (numbers above).

<assumption_delta_decision>
Primary noun: the hit target, `HitRecord.target: EntityId` and `HitTarget.id`.
Decision: no-change for the target noun, add-alongside for the hit part. Re-evaluated after PD-01 (the buoy subentity is now tracked and destructible): every target still has an `EntityId` in one namespace. The statics keep fixed ids 3 to 5; plan 18-15 gives each buoy's subentity its own fixed static target id in the reserved range (6 and 7, the advisor's suggestion), so a frangible hit becomes two ordinary records (1 % on the buoy id, the full damage on the subentity id) and `HitRecord` stays an `EntityId` record; pods and plates are store ids; the player is 100. What the beam ended on inside a target is the part, which `firstShipHit` returns beside the id as `HitPart` (`{ kind: "hull" }` or `{ kind: "subentity"; index }`); the queueing code maps a buoy's subentity part to the subentity's id.
What would force a promote: a target with several independently destructible parts that cannot each take a fixed id (for example a future station type with frangible subentities in a variable number), which would need a `(target, part)` pair in `HitRecord` and per-part state sized at run time.
Invariant test (Task 1, extended by 18-15): every `HitRecord.target` queued by `resolveShotHits` is `PLAYER_ID`, an id in `STATIC_TARGETS` (or, from 18-15, a buoy subentity id), or a live store id at queue time.
</assumption_delta_decision>
