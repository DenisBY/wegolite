# Phase 14 Plan 01: Oracle I part 1 Summary

**An independent, source-cited oracle for the NPC flight model and the idle, tumble, fly-to, fly-from and face behaviours: a strict fixture schema, float32-emulating reference maths transliterated from the pinned Oolite source, 32 fixtures, and a guard that keeps the tree free of Wegolite code.**

- **Duration:** about 35 min (the start time was not captured; the STATE entry for the phase start was 17:11 UTC)
- **Completed:** 2026-11-15T17:41Z
- **Tasks:** 2 of 2 (Task 1 was the `tracer`; its end-to-end verify passed and expansion followed)
- **Files created:** 11 (about 2,550 lines of TypeScript, plus 5 JSON fixture files)

## Accomplishments

- The fixture contract of the plan is executable: `OracleFixtureSchema` enforces the strict key list, the citation regex with `a <= b`, the dt rule (1/60 only for `rate-` ids), `stats.scannerRange`, unit orthogonal right-handed frames within 1e-9, check ticks within the horizon, tolerance 0 on discrete fields, distinct draws in [0, 1), id rules for the player, self and ships, and ordered events. `FrameRateRuleSchema` is ready for plan 14-06.
- The reference reproduces Oolite's own arithmetic: a `Mode` object rounds every stored intermediate with `Math.fround` (the `f32` mode) or not at all (`f64`); `frustration` and `successFactor` go through `Math.fround` in both modes (contract item 8). It covers `applySticks`, `applyAttitudeChanges`, `applyThrust`, `trackDestination`, `fly_range_from/to/from_destination`, `face_destination`, `performIdle/Stop/Tumble/FaceDestination/FlyToRangeFromDestination`, and the quaternion maths of `OOQuaternion.m`.
- The replay loop already has the contract's in-tick order (a) bodies move, (b) leader refresh, (c) native update, (d) proximity. Slots (b) and (d) are real functions that throw when a fixture needs them, so plan 14-06 fills them without changing the loop.
- 32 fixtures with 449 checks and a tolerance on every one. Every closed-form row (ramps, reversal, attitude directions, thrust sums, tick-1 sticks, damping values) agreed with the float64 reference to 1e-7 relative or better when the fixtures were generated, which validates the transliteration independently of the self-replay.
- The self-test (62 tests) replays every fixture in both widths, asserts every tolerance (>= 4 x measured difference + 1e-9), exact event ticks, exact discrete fields, scripted draw counts, schema strictness (14 rejected mutations), unique ids across both oracle trees, and the fround tick helper (0.5 s -> 61, 7.5 s -> 901, 10.0 s -> 1201; float64 gives 60, 900, 1200). A deliberate mutation of the roll rate failed 13 tests and was reverted.
- The guard (10 tests) scans `tests/oracles` with the TypeScript parser and refuses any specifier that is not a `node:` built-in, `zod`, `vitest` or a relative path staying inside `tests/oracles`, refuses non-literal dynamic imports and `require`, and refuses `src` path literals passed to file-system or path calls. Eight non-vacuity cases feed synthetic sources.

## Decisions Made

- **Representation fixed by the schema** (the contract left it open): vectors are `[x, y, z]`, entity id 0 means none (no target, leader or alert), `escortSlot` is an integer >= 0. Plan 14-02's fixtures and plan 14-09's runner must follow it; a mismatch surfaces as a strict-schema failure in 14-09.

- **Expected value and tolerance rule:** closed form where one exists, else the float32 (Oolite-width) replay; tolerance = 4 x max(|f32 - f64|, |f32 - closed|) + 1e-9, rounded up to two significant digits. A closed form is never the source of its own tolerance.

## Deviations from Plan

None in scope or order: both tasks executed as written. Four choices the plan left open, all recorded above or below:

**1. [Rule 2 - correctness] Stationary exact-distance pose for the 15 s fly-to frustration fixture**
- **Found during:** Task 2
- **Issue:** the fly-to `distance < last_distance` test compares a float32-rounded `successFactor` with the distance. In float64 mode a ship whose distance changes by less than one float32 step (about 5e-4 m at 5000 m) flips that decision between widths: the abeam pose showed a frustration difference of 0.031 s after 60 ticks.
- **Fix:** the frustration fixture uses a ship at rest at an exactly representable distance (10000 m), where the test is identical in both widths, and no other navigation fixture checks `frustration` or `successFactor`. This is also a hazard for the port: see "Notes for later plans".
- **Files modified:** `tests/oracles/npc/fixtures/fly-to-destination.json`
- **Commit:** `91c2b62`

**2. [Rule 1 - fixture bug found before commit] Position of a decelerating, pitching ship is not a closed form**
- **Found during:** Task 1 (stop-still fixture)
- **Issue:** the generator's closed form for positionZ disagreed with the reference by 0.0056 m because the pitch rate settles while the ship still moves, so the nose is not along +z.
- **Fix:** the two position checks were removed from `stop-still-settles-and-zeroes` and the derivation says why. No tolerance was widened.
- **Commit:** `5a5dc44`

**3. [Rule 1 - fixture bug found before commit] Frustration after the face settle is dt, not 0**
- **Found during:** Task 2
- **Issue:** `frustration = 0` on the settle tick is followed in the same update by `frustration += delta_t` (flightSpeed is 0), so the value is 0.008333, not 0.
- **Fix:** the closed forms use one fround step and the notes cite lines 4934 and 4943-4944.
- **Commit:** `91c2b62`

**4. Behaviour table in `flight.ts`.** The plan lists three reference files. The replay loop lives in `flight.ts` with a `BehaviourTable` and `navigate.ts` adds the navigation entries and `replayAll`, so Task 1's tracer replayed idle, stop-still and tumble end to end before `navigate.ts` existed, and plan 14-06 only adds table entries.

**Total deviations:** 3 fixture corrections caught before commit plus 1 structural choice. **Impact:** none on scope; all expected values are re-verified by the self-test.

## Notes for later plans

- **Plan 14-08/14-09 (port):** Oolite's `distance < last_distance` compares a float32 `success_factor` with a double distance. A float64 port that stores `successFactor` with `Math.fround` but keeps the distance in float64 makes a different "improvement" decision whenever the distance changes by less than one float32 step, which moves the `frustration` accumulator (up to 0.03 s in 60 ticks in the abeam pose). It affects only frustration events, not steering. Plan 14-19 should list it as a recorded divergence candidate; the fixtures avoid it.
- **Plan 14-06:** slots (b) and (d) are `refreshLeaderDestination` and `proximityPass` in `flight.ts`; `avoidCollisionIfAlerted` in `navigate.ts` throws until avoid collision is added. `ORACLE_BEHAVIOURS` and `ORACLE_SCAN_CLASSES` list all 39 behaviours and 16 scan classes from the Oolite tables.
- `aimPointX|Y|Z` is in `ORACLE_FIELDS` but this reference does not model the tracking curve (plan 14-02 derives it); a check on it fails loudly with NaN.
- Navigation fixtures stop steering inside the 0.99999 dead band, so ships arrive at a heading error of 0.2 to 0.4 rad. That is Oolite's 95 % rule, not a port bug.
