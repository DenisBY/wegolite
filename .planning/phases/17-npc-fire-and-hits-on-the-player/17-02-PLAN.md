**The fire-site oracle contract (binding for both sides).**
1. A fire-site fixture is `{ fixture, weapon: { forwardWeaponTemp, missedShots }, fireRequestTicks }`; an aim-feedback fixture is `{ fixture, weapon: { missedShots } }` (temperature 0). `fixture` is an `OracleFixtureSchema` object of `../schema.ts`, unchanged: the same frames, in-tick order (a) to (d), scripted `draws`, `checks`, `events`, horizon and tolerances as every Phase 14 fixture. Ids are kebab-case, unique across all oracle trees, prefixed `fire-site-`, `hot-` or `aim-feedback-`.
2. `weapon.forwardWeaponTemp` is `forward_weapon_temp` as the behaviour reads it at update 1, that is after Oolite's cooling at the top of that update (`ShipEntity.m:2214-2218`; advisor warning). No shot fires during a fixture: the gate is plan 17-01's subject. So at update k the behaviour reads the value cooled k - 1 more times in float32, `fround(max(fround(T - fround(6 x 1/120)), 0))`, and a fixture near a threshold states in its derivation the update at which the read crosses it. `forwardWeaponTemp` is a float32 value.
3. `weapon.missedShots` is constant over a fixture (it changes only when a shot resolves).
4. `fireRequestTicks` lists every update (1-based) at which the behaviour reaches a `fireMainWeapon:` call, whatever the gate would decide. `draws` lists only the steering's own draws; the gate's `randf()` (9949) is not in this contract. Check this against the source and state it in the self-test: in every in-scope method, no `randf()` or `ranrot_rand()` follows the `fireMainWeapon:` call, so moving the gate's draw after the update keeps the stream order.
5. The hot-weapon reads use `weapon_temp`, which `fireWeapon:` refreshes from `forward_weapon_temp` at its start (9914-9921) and which the tail reads after the call in the same method; so the tail sees the temperature read at that update (excluding the heat of a shot fired in it, none here). The dispatcher (4053, 4078-4089) and break-off (3932) read `forward_weapon_temp` directly. Thresholds: READY `0.25f x 256.0f` = 64; USABLE `WEAPON_COOLING_CUTOUT x NPC_MAX_WEAPON_TEMP` = `fround(0.85) x 256` as a float32 product (`ShipEntity.h:115-120`), compared float against float.
6. Recorded Phase 14 cuts stay: no afterburner, missiles or cloak; aft, port and starboard weapons are none on every compiled record and no laser is a turret, so the terms and branches that need them are unreachable and are listed, not authored, in the self-test's unreachable table (flee's 4890-4892 call, fly-to's `!isWeaponNone(aft/port/starboard)` terms at 4717, the dispatcher's RUNNING_DEFENSE and ATTACK_BROADSIDE). The accuracy-9 dodge of fly-to (4721-4729) is not modelled (Phase 14 divergence 21): a fly-to fixture may use accuracy >= 9 only where the 4713 outer condition is true (the `else if` is then skipped); keep the existing derivation's throw for the other case.
