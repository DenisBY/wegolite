<objective>
**As a** player, **I want to** have a failed arrival or a failed Load leave the scene I see and the simulation I step agreeing with each other, **so that** the session never draws one system while it simulates another.

Purpose: close the W-1 warning in 06-VERIFICATION.md (gap G-7 residual, NAV-05 and SAVE-05). In `enterSystemById`, `scenes.enterSystem` runs before the layout read and before `system`, `scene` and `layout` are assigned. A throw after the switch therefore leaves the scene on the destination while the session stays on the origin. The scene manager also installs the destination before it retires the origin, and a retire failure throws after that install, so the same split can happen inside `enterSystem`. Separately, a throw between building the destination and installing it leaves that destination built and never disposed.

Output: an `enterSystemById` that derives the destination layout before the switch and has no throwing statement after it (game-session.ts); a pre-install cleanup and a commit-point rule for `enterSystem` (scene-manager.ts); and three commit-point unit cases with a test-only observation of the destination's disposal (tests/app/dispose.test.ts).

Seam statement (stated rather than invented): no unit or integration seam exists to force a throw inside `GameSession.enterSystemById`. `createGameSession` needs a WebGL renderer, DOM roots, a probe and the save store, and no existing test constructs `GameSession`. The forced throws in this plan are therefore placed on `createSceneManager`, where the recording renderer already lets a test make `getSize` or `renderLists.dispose` throw. Observing that the destination was disposed uses a test-only `vi.mock` wrapper of `createSystemScene` that records each built scene and counts its dispose calls. The wrapper changes no behaviour and is not a production seam.

Deferred to Phase 7 (WR-04, not yet owner-accepted; the re-verifier decides acceptance): the W-2 browser negative control for the throw path is deferred. WR-04 in the Deferrals table of 06-GAP-CLOSURE.md records it as Deferred with owner Phase 7 test-seam work, and the G-7 row there is recorded as closed with explicit deferral. This plan does not claim owner acceptance, adds no browser seam, and does not change the ledger row.

Structural truths: some truths describe failure-path ordering that no executable test reaches, because no test constructs `GameSession`. Those truths are marked structural in `must_haves`, and their check is the grep acceptance in Task 1.

Scope note: `start()` (around line 2552) and `performSwap()` (around line 2788) also call `scenes.enterSystem`. `start()` runs before any session state exists, and `performSwap()` already reads the layout with the `??` fallback. Neither can split a live session, so neither is edited here. Both gain the scene manager's pre-install cleanup and commit point from the second task. `enterMenu` has the same build-then-apply-viewport shape, but it is not on any arrival or Load path, so it is out of scope and unchanged.

Framing source: the user story above comes from the W-1 entry in 06-VERIFICATION.md and the G-7 ledger row. The ROADMAP phase Goal line is not written as a user story, so this plan does not derive its framing from it.
