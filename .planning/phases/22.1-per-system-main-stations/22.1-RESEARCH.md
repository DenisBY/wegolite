## Summary

Oolite picks the main station with one line, `Universe.m:1550`: the system's `station` key, default `"coriolis"`, is used as a ship *role*, and the one ship with that role is built. The vendored `planetinfo.plist` (byte-identical to the checkout and to the pin) holds exactly 1,824 `coriolis`, 167 `dodecahedron` and 57 `icosahedron` systems, and Wegolite's compiled `systems/g*.json` already carries the same three values in `system.station` (a bare `z.string()` today). The three stations are three shipdata templates that differ only in model, name, role, dock position and sub-models: same `station_roll`, `max_energy`, `market_monitored = yes`, 14 flashers each. So the phase is **data-driven**: the per-system choice, the dock port, the mass and the collision radius all fall out of the existing build-time pipeline (`ship-mass.ts`, `ship-radius.ts`, `dock-port.ts`, `static-hulls.ts`, `glb.ts`) once it is fed the two new stations instead of a Coriolis-only constant.

Three findings change the roadmap's wording and must reach the plans. (F2) The `tunnel_*` keys are not dock geometry: in Oolite they only shape the docking *break pattern* rings, none of the three main stations authors them (all use the defaults 4 / 45 / 2.67), and Wegolite deliberately draws no break pattern. The real dock port is the dock subentity's mesh bounding box (`DockEntity.m:1044-1045`), already what `dock-port.ts` measures; the "six-sided slot" is the Rock Hermit (out of scope). The three slots are all rounded rectangles: Coriolis 103.4 x 241.9 m (portrait), Dodecahedron 210.4 x 81.0 m (landscape), Icosahedron 82.1 x 238.5 m (portrait). (F3) Aegis does not depend on the station: `sd2 < SCANNER_MAX_RANGE2 * 4.0f` (51,200 m) for every station, so "aegis per station" reduces to a test that the range is unchanged; the only station-radius consumers are the torus factor, the `STATION_AEGIS` populator shell, the ident sphere and NPC proximity, all already generic over `layout.station.radius`. (F5) The mass is what changes behaviour: Wegolite's own mass/radius code, run over the checkout meshes, reproduces the Coriolis bit for bit (515,483,904 / 779.3702392578125) and previews the Dodecahedron at 912,357,312 (blockage radius 9,551.7 m, radius 832.209 m) and the Icosahedron at 826,313,024 (9,090.2 m, radius 940.793 m); these are previews until the container measures them.

The hard part is not the numbers but the **singleton assumptions**: the session builds one `stationDef`, one `stationKey`, one `DockGeometry` and one Coriolis GLB at boot and never rebuilds them on a hyperspace arrival (`hyperspace-controller.ts` comment "never rebuild the dock port"). Every one of those must become a function of the current system, and the hyperspace arrival swap is synchronous, so the destination's heavy assets (hull octrees, GLB, textures of 3-5 MB per station) must be loaded before the jump completes.

**Primary recommendation:** Extend the existing compile pipeline to three stations (add the two shipdata keys to `CLIENT_SHIP_KEYS`, per-kind dock-port and hull records, a generalised station GLB builder), pass the sim a small `StationSpec` through `deriveSystemLayout` (so `src/sim` holds no station literal), keep every Coriolis artifact byte-identical, and gate the whole thing with measured fixtures committed first, a content-vs-fixture pin test, and a source-scan tripwire guard.

## Findings

### F1. How Oolite chooses the main station [VERIFIED: /home/opencode/git/oolite/src/Core/Universe.m:1550]

`stationDesc = [systeminfo oo_stringForKey:@"station" defaultValue:@"coriolis"];` then `a_station = (StationEntity*)[self newShipWithRole:stationDesc];` (Universe.m, `setUpSpace`, "space station" block). If the result is not a valid station it retries with `defaultStationDesc`, then falls back to `newShipWithName:@"coriolis-station"`. After creation: orientation `quaternion_rotation_between(vf, (0,0,1))`, `setScanClass:CLASS_STATION`, `setAllowsFastDocking:true`, allegiance `galcop`. Nothing else depends on the kind.

Role to ship key mapping, from `shipdata.plist` [VERIFIED: shipdata.plist:1739, 1920, 2377]:

```
roles = "coriolis station";                        -> coriolis-station     (1738 name = "Coriolis Station";)
roles = "dodo dodec dodecahedron station";         -> dodecahedron-station (1919 name = "Dodecahedron Station";)
roles = "ico icosa icosahedron station";           -> icosahedron-station  (2376 name = "Icosahedron Station";)
```

Each is a `like_ship` of its `oolite_template_*-station` (shipdata.plist:4402, 4406, 4429-4431). No other non-template ship carries these roles (`rg 'roles = ".*(coriolis|dodecahedron|icosahedron)'` hits only those three lines), so the role lookup is deterministic. Wegolite therefore needs only a three-entry map `coriolis|dodecahedron|icosahedron` to `<kind>-station`.

### F2. `tunnel_*` is the break pattern, not the dock port [VERIFIED: Universe.m:2897-2899, shipdata.plist:3361-3363, DockEntity.m:1044-1045]

```objc
sides = [info oo_unsignedIntForKey:@"tunnel_corners" defaultValue:4];
startAngle = [info oo_floatForKey:@"tunnel_start_angle" defaultValue:45.0f];
aspectRatio = [info oo_floatForKey:@"tunnel_aspect_ratio" defaultValue:2.67f];
```

These three lines are the only readers in `src/` and sit in the docking *break pattern* (`OOBreakPatternEntity` rings, `forDocking`). The only shipdata entry that authors them is the Rock Hermit (`tunnel_corners = 6; tunnel_start_angle = 0; tunnel_aspect_ratio = 1;`, shipdata.plist:3361-3363), which is out of scope. None of `oolite_template_coriolis-station`, `-dodecahedron-station`, `-icosahedron-station` authors a `tunnel_*` key, so all three draw the same 4-sided 45-degree 2.67-aspect rings. Wegolite draws no break pattern (owner decision 2026-11-18, quick 261118-l26; FIDELITY row "Launch presentation: a 1.5 s pre-roll in the dock slot ..."), so **nothing in this phase reads `tunnel_*`**. The roadmap's "six-sided slot" decision and the `tunnel_*` measurement item are moot for the main stations; the measurement still records the three defaults (cheap, closes the question).

The port dimensions are the dock subentity's own bounding box: `BoundingBox bb = [self boundingBox]; port_dimensions = make_vector(bb.max.x - bb.min.x, bb.max.y - bb.min.y, bb.max.z - bb.min.z);` (DockEntity.m:1044-1045). Wegolite already does exactly that in `tools/oolite-ingest/convert/dock-port.ts` (extents of `oolite_coriolis_dock.dat`). Bounds read from the checkout this session [VERIFIED: scratch script over /home/opencode/git/oolite/Resources/Models]:

| Dock mesh | x extent | y extent | z extent (depth) | Orientation |
|-----------|----------|----------|------------------|-------------|
| `oolite_coriolis_dock.dat` | 103.4123 | 241.888 | 250 | portrait (taller than wide) |
| `oolite_dodo_dock.dat` | 210.362 | 81.0268 | 250 | **landscape** (wider than tall) |
| `oolite_ico_dock.dat` | 82.1076 | 238.546 | 273.278 | portrait |

Consequence: the launch twist predicate `slotTwistedForShip` (`corridor.ts`, `(port.width < port.height) ^ (ship.width < ship.height)`, Oolite `DockEntity.m` twist test) is true for Coriolis and Icosahedron and **false for the Dodecahedron** (Cobra is wider than tall), so the Dodecahedron launch is untwisted. The sim already reads `dock.port` and `dock.ship` (`launch.ts`), so this is automatic once the per-station `DockGeometry` is supplied; only the comments that say "the Coriolis slot (taller than wide)" are stale. The corridor half-extents `ww/hh` (x1.25 expansion to 90 %) and `port.depth` likewise come from the record. `DockEntity.m` also computes a `port_corridor` from `[station boundingBox]` (DockEntity.m:1044+ `setDimensionsAndCorridor`); Wegolite does not model it today (no station-bbox corridor), so it is not a per-station gap.

### F3. Aegis and scanner are station-independent [VERIFIED: ShipEntity.m:6699]

`if (sd2 < SCANNER_MAX_RANGE2 * 4.0f) // double scanner range` with `sd2` the squared distance to `[UNIVERSE station]`'s position. No mass, radius or kind enters. Wegolite's `STATION_AEGIS_RANGE = 51_200` (layout.ts:76) and `aegis.ts` are therefore correct for all three. **Do not make aegis per-station**; add one test per kind that the range is 51,200. Station-radius consumers (all already read `layout.station.radius`): `torus.ts:58-65` (nearest-surface distance for the torus factor), `placement.ts:246` (`layout.station.radius * 1.2`, Oolite `Universe.m:1812` `[[self station] collisionRadius] * 1.2`), `combat/ident.ts:92`, `npc/proximity.ts:278`. They change automatically (and only for non-Coriolis systems) when `layout.station.radius` is per-kind.

### F4. Mass and collision radius derivation [VERIFIED: ShipEntity.m:419, 2028-2044; Wegolite ship-mass.ts, ship-radius.ts]

- Hull mass: `mass = (GLfloat)(density * 20.0f * [octree volume]);` (ShipEntity.m:419).
- Each solid subentity adds `mass += [subent mass];` and the collision radius grows to `HPmagnitude([subent position]) + [subent findCollisionRadius]` when larger (`addSubentityToCollisionRadius:`, ShipEntity.m:2028-2044). Flashers add nothing.
- Wegolite ports both at build time (`tools/oolite-ingest/convert/ship-mass.ts` `shipMass`, `ship-radius.ts` `collisionRadius`) and compiles `mass` and `collisionRadius` into `ships-client.json` for `CLIENT_SHIP_KEYS` (`ships.ts:544-548`: `"buoy", "coriolis-station", "oolite_template_cobra3-player"`). Quick 261117-jji measured the Coriolis in a running Oolite 1.93.1-255: mass 515483904 and radius 779.3702392578125, both EQUAL to Wegolite.
- Both functions are generic over the catalogue and the parsed meshes; they need only the new `.dat` files parsed.

### Pattern 1: Compile everything per kind from one table
**What:** one `STATION_KINDS` table in the content tool lists, per kind, the ship key, the hull/faceplate/tris/dock model files and the GLB name; `CLIENT_SHIP_KEYS`, `MODEL_SOURCE_FILES`, `EMITTED_ENTRIES`, the dock-port and hull emitters all read it.
**When to use:** every compile site in C1-C9. It removes the four-file destructuring in `emitModels` and the Coriolis literals in `dock-port.ts`.
**Example:**
```typescript
// Source: this research; shape follows tools/oolite-ingest/convert/ships.ts CLIENT_SHIP_KEYS
export const STATION_KINDS = [
  { kind: "coriolis",     key: "coriolis-station",     glb: "coriolis.glb",     dock: "oolite_coriolis_dock.dat",
    hull: ["oolite_coriolis.dat"], extras: ["oolite_coriolis_tris.dat", "oolite_coriolis_faceplate.dat"] },
  { kind: "dodecahedron", key: "dodecahedron-station", glb: "dodecahedron.glb", dock: "oolite_dodo_dock.dat",
    hull: ["oolite_dodo.dat"], extras: ["oolite_dodo_faceplate.dat"] },
  { kind: "icosahedron",  key: "icosahedron-station",  glb: "icosahedron.glb",  dock: "oolite_ico_dock.dat",
    hull: ["oolite_ico.dat", "oolite_ico_hull.dat"], extras: [] },
] as const;
```

### Pattern 2: The sim gets a spec, never a literal
**What:** `StationSpec` is a plain structural type in `src/sim/world` (the sim cannot import the catalogue, but can declare the shape the app passes in, as `DockPortData` does). `deriveSystemLayout(system, spec)` copies `radius`, `mass`, `key`, `name` onto the layout; `buildStepOptions` reads `layout.stationMass`; `statics.ts` resolves the station row from `layout.stationKey`.
**When to use:** removes S1, S4, S5, S6 and A7 literals; the literal-pin tests (`CORIOLIS_STATION_MASS` equals compiled) become "layout carries the compiled value".
**Example:**
```typescript
// Source: this research; modelled on src/sim/dock/geometry.ts DockPortData
export interface StationSpec {
  readonly kind: "coriolis" | "dodecahedron" | "icosahedron";
  readonly key: string;            // hull table key = ident key = save key
  readonly name: string;           // Oolite ship name, e.g. "Dodecahedron Station"
  readonly collisionRadius: number;
  readonly mass: number;
  readonly dockOffset: number;     // |dock subentity z|
  readonly stationRoll: number;    // right angles per second
}
```

### Pattern 3: Per-system installs at every system change
**What:** one function `stationFor(system)` in the app returns `{ spec, dockGeometry }`; it is called at boot (after the saved system is resolved), `loadFromSave`, and `enterSystemById`. `ctx.core.stationDef/stationKey/dockGeometry` are assigned in the same "commit point" block as `ctx.core.system/scene/layout` (hyperspace-controller.ts:98-115). The records for all three kinds are small (a dock-port record is 514 bytes) and are loaded eagerly with the catalogue; only the heavy assets are lazy.
**When to use:** A1-A6.

### Anti-Patterns to Avoid
- **A station literal in `src/sim`**: it is exactly what the new guard fails on. Pass data in.
- **Making aegis or the scanner per-station**: Oolite does not (F3).
- **Reading `tunnel_*`**: nothing to read for these stations (F2).
- **Re-baselining a Coriolis golden to "make it pass"**: a moved Coriolis hash is a bug in the seam, not a golden to refresh.
- **Hand-editing generated data**: AGENTS.md; regenerate with `docker compose run --rm assets`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Station mass and radius | typed constants copied from the container | `shipMass`, `collisionRadius` over the vendored meshes, pinned to the measured fixture | the same code reproduced the Coriolis bit-exact; the fixture keeps it honest |
| Dock aperture and corridor | per-station typed numbers | `emitDockPort` from the dock mesh bounds + `createDockGeometry` | Oolite derives the port from the dock bbox (DockEntity.m:1044-1045) |
| Launch twist and slot shape | a per-station launch rule | `slotTwistedForShip(dock.port, dock.ship)` | already evaluates Oolite's predicate from data |

## Common Pitfalls

### P1: A Coriolis artifact moves while "just adding two stations"
**What goes wrong:** regenerating content changes `ships.json`/`manifest.json`/`texture-encodings.json` goldens (expected, mechanical) but also, by accident, the Coriolis GLB, dock-port record or `ships-client.json` Coriolis entry.
**Why:** a shared builder (`buildStationGlb`) or `MODEL_BOUNDS` edit that reorders nodes, or `CLIENT_SHIP_KEYS` order changing the `ships-client.json` entry order.
**How to avoid:** assert in the plan that `public/models/coriolis.glb`, `dock-port.json` and the Coriolis entry (including its position in the array and its mass/radius) are byte-identical before and after (`git diff --stat` on those paths must be empty; for `ships-client.json` diff only added entries). Keep `dock-port.json` and its golden as they are.
**Warning signs:** `tests/golden/content/dock-port.json` or `tools/oolite-ingest/convert/glb.test.ts` Coriolis pins change.

### P2: The singleton survives a hyperspace arrival
**What goes wrong:** the player jumps from Lave to Zaonce and docks with Coriolis geometry (corridor, contact box, mouth offset) because `ctx.core.dockGeometry` and `stationDef` were built once. The layout's `dockOffset` and the `DockGeometry` disagree and `createDockGeometry` is never re-run.
**How to avoid:** A1-A6 move together; one test per transition (boot, Continue, F2 Load, jump) asserts `layout.stationKey`, `dockGeometry.port` and the rendered model key agree with `system.station`.

### P3: Heavy assets are missing at the synchronous arrival swap
**What goes wrong:** `handleHyperspaceJumped` installs the destination scene synchronously; a not-yet-loaded Icosahedron GLB (5+ MB with textures) throws "requested before preload" and trips the "Hyperspace arrival failed" surface.
**How to avoid:** load the destination kind's assets before the countdown can complete (start when the target is committed and again at H, the countdown is 1,800 fixed steps = 15 s); after the first in-flight frame, prefetch all three kinds in the background like the NPC prefetch (outside the cold-start ceiling by exclusion). If a model is still missing at arrival, fall back to loading and holding the swap, never to a throw; or (interim between halves a and b) draw the already-loaded Coriolis GLB. Decide in planning (O3).

### P4: Static-hull artifact caps
**What goes wrong:** adding the Dodecahedron and Icosahedron octrees to `ships-static-hulls.json` fails the schema (`MAX_STATIC_HULL_ARTIFACT_BYTES = 270_000`, committed file 205,542 bytes) [VERIFIED: `ls -l`, schema constants]. Octree JSON sizes measured this session: Coriolis parts 76,829 + 15,421 + 72,089 + 4,263 B; Dodecahedron 99,435 + 2,839 + 4,097 B (about 106 KB); Icosahedron 13,165 + 113,105 + 4,097 B (about 130 KB).
**How to avoid:** per-kind hull files loaded on demand (recommended), keeping `ships-static-hulls.json` byte-identical; or raise the caps deliberately with a measured justification. A missing hull only means the station is not a laser candidate (`step.ts:613` `if (!hulls.has(row.hullKey)) continue;`), so lateness degrades gracefully but must be tested.

### P5: Render node contract is four fixed names
**What goes wrong:** `createStation` calls `requireNode` for `hull, faceplate, tris, dock` and throws for a GLB without `tris`.
**How to avoid:** the record (or the GLB) lists the node names; `NODE_ORDER` and `NODE_NAMES` come from it. Material emissive handling (`applyAuthoredEmissive`) is unchanged. For the Icosahedron decide what `hull` means (the front-section `oolite_ico.dat`) and name the `oolite_ico_hull.dat` part (e.g. `mainhull`) so polygon-offset and render order are explicit.

### P6: The dock-port "hull" box for the Icosahedron
**What goes wrong:** `dock-port.ts` builds `hull` from one main model, but the Icosahedron's real hull is the subentity `oolite_ico_hull.dat` (±643 on all axes) while `oolite_ico.dat` is only a front section (z 397..648). Using the front section alone gives a proxy far smaller than the station.
**How to avoid:** `hull` = union of the main model and every solid subentity box; `contact` = union incl. faceplate-like parts; keep the schema invariant `contact.zMin <= hull.zMin` (dock-port schema line 125). Preview protrusion past the mouth: Dodecahedron faceplate z max 586.057 vs mouth 560.3216 (about 25.7 m), Icosahedron 648.127 vs 642.8881 (about 5.2 m), Coriolis 534.298 vs 500.2561 (34.04 m). The contact proxy is a conservative box (D-06), so a box around a pentagonal or triangular front face is a looser fit than for the Coriolis: record this limitation, do not widen the scope to octree collision (E-135).

### P7: `StaticTarget` is a frozen module-level table
**What goes wrong:** `STATIC_TARGETS` is `Object.freeze`d and read by 7 modules; making the station row dynamic by mutation breaks purity and determinism.
**How to avoid:** keep the table, replace the two station literals with a single reserved key (for example `hullKey`/`identKey` resolved through `staticHullKey(row, layout)`), so the table stays frozen and the layout supplies the key; update the consumers listed in S6.

### P8: Census and per-kind layouts
**What goes wrong:** `tests/helpers/population-census.ts` uses the Coriolis def for all 2,048 systems and the census golden (`tests/golden/world/population-census.json`: `worlds 40960`, `mean 45.313281`, `median 44`, `p95 78`, `p99 94`) records only ship counts. If the helper is switched to per-system stations, the `STATION_AEGIS` shell uses the other radius and the rejection loop (`placement.ts:240-251`) could consume a different RNG sequence in rare cases, which could move counts for the 224 non-Coriolis systems.
**How to avoid:** do not change the golden's meaning silently: first run the census with per-system stations and record whether anything moves. The shell inner radius is about 0.8-0.9 km against an outer 51.2 km, so a rejection is about a 4e-6 event per draw [ASSUMED estimate, measure]; if nothing moves, switch the helper to the production seam (it claims "the production path") and keep the golden; if something moves, the Coriolis systems must still be byte-identical and the diff must be only non-Coriolis rows (report, owner-visible). The golden stores aggregates, so verify per-system rows with a temporary per-system dump under `/tmp`.

### P9: Exposure derived from the Coriolis face
**What goes wrong:** `src/render/exposure.ts` derives the sun intensity from the measured mean Coriolis face luminance (comments at lines 30-70) so a lit Coriolis does not clip. The Dodecahedron and Icosahedron faces have other luminance; blown or dim stations are a visual regression nobody tests.
**How to avoid:** half (b): compute the mean face luminance of the new diffuse maps at build time, compare with the Coriolis constant, and only change the global exposure if a station clips (O5). Do not retune the Coriolis path.

### P10: A guard that is green because it scans nothing
**What goes wrong:** the new "no Coriolis-only constant" guard passes vacuously after the constants are renamed.
**How to avoid:** follow the repository pattern (tripwire with synthetic positive inputs, e.g. `tests/guards/hull-wear-tripwire.test.ts`): the guard must have a synthetic source that fails each rule, and a check that the allow-listed file really contains the tokens. ## Byte-identity design (criterion 1)

What a Coriolis system hashes or pins, and why it stays identical:

- **B1 World snapshot and twin hash.** `World.station` is `StationRecord { alert, launched, marks }` (`world.ts`, "Hashed only when not pristine") and holds no kind; `hashWorld` reads no layout number. The station kind is a pure function of the system, so it enters no hash. Do **not** add a kind field to `StationRecord`, to the snapshot, or to `hashWorld`.
- **B2 Layout numbers.** `deriveSystemLayout` for a Coriolis system must return the same doubles: radius 779.3702392578125, `dockOffset = Math.abs(500.2561)`, `stationRollRadPerSec = (0.08 * Math.PI) / 2`. - **B3 Hull table.** The sim reads the station hull by key; with the Coriolis row resolved from `layout.stationKey === "coriolis-station"` the lookup is identical. `fullHullTable()` (tests/helpers/hull-table.ts) must keep returning `coriolis-station` under the same key and the same data.
- **B4 Census.** See P8. The census golden aggregates all 2,048 systems, so it is the one pinned artifact that **could** move through non-Coriolis rows; the Success Criterion 1 wording is about Coriolis systems. Plan: measure first, then decide.
- **B5 Saves.** Save format v5 is unchanged (the key was already saved); `tests/golden/save/*.json` carry `coriolis-station` and must still load.
- **B6 Content goldens.** `tests/golden/content/ships.json`, `manifest.json`, `texture-encodings.json`, `ships-client` pins, `ships-static-hulls.json` golden (if the file stays as is, no move) will change only by added entries; the Coriolis entries and bytes must be asserted equal.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Forged `station.key` in a save selecting an unvalidated record | Tampering | allow-list from the catalogue (`save.ts:563, 747`); derive the live station from the system, treat the saved key only as a validated label |
| Corrupt or oversized generated station records or octrees (DoS) | Denial of service | strict zod schemas with the existing node/byte caps (P4) and named `DockPortError`-style failures |
| Path escape in the GLB/texture loader | Tampering | the anchored `models/<name>.glb` pattern; paths only from the compiled record |
| Supply chain: vendored bytes | Tampering | `--export-pin` verifies against the pinned git blobs and refuses digest changes; no new npm package |
