## 22.1-01

**Summary**
A well-shaped measurement-first plan: three Oolite runs (spawned stations, Zaonce, Biarge), a numbers-only fixture, an oracle test that is a tripwire for the two pending kinds, and a documentation/decision task. The tracer ordering (Coriolis first through the whole route) is exactly right for an environment-dependent task. The weak points are the fixture schema (number-vs-string ambiguity), an over-specified PROJECT.md rationale that records measurements the executor may not be able to reproduce, and a `station_roll` reading whose JS property semantics are doubtful.

**Strengths**
- Tracer discipline: Task 1 proves probe → container → log → fixture → oracle against values 261117-jji already found EQUAL, before any unknown is measured. That is the correct de-risking order for a plan whose failure mode is "the container will not cooperate".
- The MS-2 mismatch rule (EQUAL / ROUNDING ≤ 1e-6 / DIFFERS stops the plan) is carried from the quick task and, importantly, the plan forbids committing a DIFFERS or rounding a measurement.
- `PENDING_KINDS` asserting *absence* of the two entries in `ships-client.json` is a genuinely good tripwire: it fails the instant 22.1-02 compiles a kind, forcing the oracle on rather than letting it rot skipped.
- Prohibitions and threat T-22.1-01 correctly keep the probe OXP, `Latest.log`, saves and screenshots out of the repo (CC BY-NC-SA output; `tools/oolite-reference/README.md`).
- Task 3's ROADMAP correction of the `tunnel_*` premise is backed by the verified fact that the only readers are the break-pattern code (`Universe.m:2897-2899`), so it is a documentation fix, not a silent scope cut.

**Concerns**
- **MEDIUM — fixture schema is internally inconsistent.** Task 1 says "every float is a finite numeric string" and "every float is printed with `String(value)`", yet the sample fixture stores `boundingBox`, `position`, `orientation` as JSON numbers and only `mass`/`collisionRadius` as strings. A validator written to the prose would reject the example; one written to the example would not enforce the stated rule. `compareMeasured(measured: string, compiled: number)` silently assumes the former.
- **MEDIUM — Task 3 writes unverifiable measurement claims into PROJECT.md.** The rationale asserts "0 of 40,960 digest rows differ … 0 worlds of 1,856,032 ships" and cites a plan-time scratch run. Those scripts lived in a session scratchpad (the plan itself says "possibly gone", `/tmp/claude-1027/...`). The executor of 22.1-01 is asked to record a claim it cannot re-derive, and 22.1-08 then "measures again". Either the claim belongs only in 22.1-08's SUMMARY, or 22.1-01 must re-run the dump itself.
- **MEDIUM — `station_roll` via `ship.roll` is questionable.** In Oolite, `ship.roll` on a ship entity is an orientation/attitude accessor, not the shipdata `station_roll` key (0.08, compiled). Measuring `ship.roll` may yield an angular rate or a quaternion-derived value, which will then be compared against a compiled 0.08 by MS-2 and may produce a spurious DIFFERS. The authoritative value is the shipdata entry, which the content build already carries (`ships-client.json` `extras.station_roll`, `shipDef.stationRoll`).
- **LOW — the "two real main stations" proof is weaker than claimed.** Run B logs `dataKey/mass/collisionRadius` of `system.mainStation`. Since Oolite builds the ship from the same shipdata template, this can only confirm the role mapping; it cannot catch a mass difference between "spawned" and "built" because there is no separate built mass. The plan's own text ("proving the spawned and the built station have the same …") overstates what the measurement establishes.
- **LOW — steps-file/menu arithmetic is under-specified.** "the scenario row selected with `key Down` presses; the comment states the menu arithmetic used" pushes a fragile, order-dependent interaction into executor judgement, on a remote machine where each iteration costs a container run.
- **LOW — no time budget/failure path for the remote.** `--timeout 300` × 3 runs plus iteration on the probe is the largest wall-clock risk in the phase; nothing says what to do if the reference image is absent (research's Environment table says "not checked").

**Suggestions**
- Rewrite the fixture schema explicitly: floats that must survive float32 exactness (`mass`, `collisionRadius`, dock `boundingBox`) are `String(v)`; positions/orientations are numbers. Then `compareMeasured` takes `(measured: string | number, compiled: number)` or the validator converts.
- Move the census claim out of 22.1-01's PROJECT.md text into 22.1-08; here record only the decision (D-A) and the procedure.
- Drop `ship.roll`; log the shipdata `station_roll` via `Ship.shipDataForKey(key)` (the probe already reads the dictionary for `tunnel_*`) and the compiled value as a cross-check.
- State the probe's failure strategy: if `/tmp/ooref-mass` is gone, rebuild from the quoted shape in `261117-jji-SUMMARY.md`; if the reference image is missing on the remote, stop and report rather than improvise.

**Risk Assessment**
**MEDIUM.** The plan is the right shape and its tracer is sound, but it front-loads an environment-dependent measurement with two ambiguity traps (fixture typing, `ship.roll`) and one documentation claim the executor cannot verify. All are cheap to fix before execution.

## 22.1-02

**Summary**
Solid, narrowly scoped: vendor six meshes through the pinned-export route, add a single station record, extend `CLIENT_SHIP_KEYS`, add `MODEL_BOUNDS`, tighten `system.station` to an enum. The byte-identity discipline is explicit and testable. Two mechanism errors and one ownership gap need fixing: the `ships-client.json` ordering claim is wrong about *why* the order comes out right, the `stationShip` deletion breaks a test file the plan does not own, and the "market_monitored" assertion is described as covering an implied-work clause whose actual scope is narrow.

**Strengths**
- Vendoring through `scripts/vendor-oolite.sh --export-pin` plus `CHECKSUMS.sha256`/`pin.json`/`ASSETS.md`/`NOTICE` is the only acceptable route under AGENTS.md rule 4, and the plan says so three times (prohibition, threat T-22.1-04, action).
- The plan deliberately does **not** add GLB entries, so `VENDORED_MODEL_FILES`/`modelVendored`/`ships.json` cannot move; the byte-identity claim for `ships.json`, `dock-port.json`, `coriolis.glb` and every `systems/g*.json` is checkable with `git diff --exit-code 5deddef5`.
- `readModels` extended to the union of `MODEL_SOURCE_FILES` and `STATION_MODEL_FILES` is the minimal change that lets mass/radius compile without emitting a model — correct and low-risk.
- `z.enum(STATION_KINDS)` imported from `src/content/stations.ts`, and the "no runtime import" constraint on that module (because `ships.ts` uses `import.meta.glob`) shows real awareness of the Node-content-tool constraint.
- O8 handling (`missing key → DEFAULT_STATION_KIND`, bad value → SCHEMA error) is explicit and matches Oolite's default-with-fallback.

**Concerns**
- **MEDIUM — the ordering mechanism is misstated.** The truth says "`CLIENT_SHIP_KEYS` … in code-unit order" and the behaviour says "keys in order: buoy, coriolis-station, dodecahedron-station, icosahedron-station, oolite_template_cobra3-player". The array order is fine, but `emitClientShips` filters **catalogue order** (`tools/oolite-ingest/convert/ships.ts:550-566`), and `ships.json` already holds dodecahedron/icosahedron before the cobra. So the expected output is right for the wrong reason; an executor who "sorts by key" would produce a different file and break the pinned index check.
- **MEDIUM — the `stationShip` deletion is not fully owned.** `stationShip` is used by `tests/content/ships-client.test.ts:21,104,108`, not only by `start-session.ts:574`. Plan 22.1-04 deletes it and lists `tests/content/player-ship.test.ts` but not `ships-client.test.ts`; 22.1-02 lists `ships-client.test.ts` but its action says only "extend" it (the market-monitored assertion). Between the two plans nobody is told to remove that import, and the result is a typecheck failure attributed to whichever plan runs second.
- **MEDIUM — "market_monitored" assertion may pass vacuously or fail for the wrong reason.** The compiled `extras.market_monitored` is carried from shipdata; the shipdata templates do author it (`shipdata.plist:1706,1895,2352`). But the test is asked to "widen the test's local `Entry` type with `extras` rather than casting" — that is a test-shape instruction, not an assertion about the *presence* of the field for the new kinds before 22.1-03 adds their records. If shipdata carries it as a string `"yes"` converted to boolean, the assertion `=== true` depends on a conversion the plan does not point at.
- **LOW — `MODEL_BOUNDS` "re-measured; the research values are a cross-check" is right but has no stated tolerance.** `assertBounds` fails on any mismatch; if the research extents came from a different parse, the first `assets` run fails and the executor must guess whether to trust the build or the research.
- **LOW — the phase-estimate confidence is "low" for a plan with 26 paths.** The scope note argues 12 are vendored/generated and 6 tests; fair, but the vendoring step alone is a review-heavy change (licence rows, digests).

**Suggestions**
- Replace "in code-unit order" with "in catalogue order, which for these keys is buoy, coriolis-station, dodecahedron-station, icosahedron-station, oolite_template_cobra3-player" and keep the index assertion.
- Explicitly assign the `tests/content/ships-client.test.ts` edit to 22.1-02 (it is already in `files_modified`): "remove the `stationShip` import and the two assertions that depend on it; do not wait for 22.1-04."
- State the `market_monitored` conversion path (`shipdata "yes"` → `extras` boolean) and assert the compiled value, not the shipdata text.
- Add one sentence on `MODEL_BOUNDS`: record the build-reported extents, and treat a research mismatch as a plan finding (report), not a silent overwrite.

**Risk Assessment**
**MEDIUM.** Low intrinsic complexity, but the ordering misstatement and the split ownership of the `stationShip` test edit will surface as a red typecheck or a surprising golden diff. Both are one-line fixes in the plan text.

## 22.1-03

**Summary**
The most carefully reasoned content plan: per-kind dock-port and hull files, the Coriolis left byte-identical by construction, the Icosahedron hull-union subtlety (front section vs `oolite_ico_hull.dat`) caught, and the octree caps handled by on-demand files rather than a raised shared cap. The main risks are the byte-identity proof being asserted rather than mechanised, and one silent behavioural dependency (a missing hull makes the station a non-candidate) that is mentioned but not tested here.

**Strengths**
- Choosing per-kind files over one keyed file is justified by the byte-identity requirement: `tests/golden/content/dock-port.json` stays the Coriolis proof. This is the right trade-off and the plan says why.
- Pitfall P6 is handled concretely: `hullModels` for the Icosahedron is `oolite_ico.dat` + `oolite_ico_hull.dat`, `contactModels` is both, and `contact.zMin <= hull.zMin` is kept (`src/content/schemas/dock-port.ts:125`).
- Avoiding `MAX_STATIC_HULL_ARTIFACT_BYTES` (270,000 B, `src/content/schemas/ship-static-hull.ts`) is correct: the measured octree JSON totals ~236 KB for the two stations, plus the existing 205,542 B file, so a shared file would need a cap change for no benefit.
- The HUD guard extension to every `ships-static-hulls*.json` name is a nice catch: ident strings for the new stations otherwise never reach the message-length budget.
- Named errors at the boundary (`DockPortError` naming the file) and re-validation in `createDockGeometry` matches the existing pattern.

**Concerns**
- **MEDIUM — "the Coriolis bytes equal the golden" is asserted as a behaviour, but nothing produces that comparison.** The behaviour says "the Coriolis bytes equal `tests/golden/content/dock-port.json`"; the acceptance says `git diff --exit-code`. That works only if the emitter's output for the Coriolis is unchanged, which depends on `measureDockPort` preserving float formatting and key order. Worth an explicit "emit then compare against the current file byte-for-byte" step (the build is deterministic, so this is cheap).
- **MEDIUM — the "no hull ⇒ no laser candidate" degradation is stated but not tested here.** 22.1-03 ships the artifacts; 22.1-06 exercises the no-hull path with a table that "lacks a new kind's artifact". The gap between "artifact exists" and "artifact is loaded" is exactly where a silent regression (station immune to lasers) lives. A one-line assertion in 22.1-03 that `loadStationHulls("icosahedron")` resolves the key would help.
- **LOW — `loadStationDockPort` glob widening (`./generated/dock-port*.json`) also matches `dock-port.json`**; the kind-to-file mapping must therefore be explicit in `STATION_RECORDS.dockPortFile`, which the plan does. Fine, but the loader must not rely on the glob to disambiguate.
- **LOW — the per-kind `dock-port-<kind>.json` schema reuse depends on `hull` meaning "the union"** for the Icosahedron; downstream consumers (`render-driver` uses `contactPort`, tests use `hull`) will see a much larger hull box than for the Coriolis. The plan says this is a conservative proxy, but the exposure of `hull` to tests makes it worth a comment in the schema file.
- **LOW — "about 106 KB / 130 KB" sizes are research measurements**, not emitted sizes; the SUMMARY obligation covers it, but a cap decision based on them would be premature.

**Suggestions**
- Make the Coriolis byte-identity a two-step check in Task 1: capture `sha256` of `src/content/generated/dock-port.json` before, re-emit, compare after.
- Add the `loadStationHulls(kind)` key-resolution assertion to Task 2 (cheap, kills the "silently immune" class of bug).
- State that `hull` is the union for all kinds and document the Icosahedron's larger proxy box in `src/content/schemas/dock-port.ts`.

**Risk Assessment**
**LOW-MEDIUM.** The design is sound and the risky part (octree caps) is avoided rather than negotiated. The remaining risk is mechanical byte-stability, which the acceptance already checks.

## 22.1-04

**Summary**
The keystone plan, and mostly well done: `StationSpec` as the sim's data door, `stationSpecFor` with named errors, the layout signature change with byte-identity for Coriolis layouts, and a boot install from the starting system with an explicitly declared interim. It is also the plan with the most migration surface and the most opportunities for a silent break: `tools/ai-harness/populator-record.ts` and `tests/sim/world/buoy-clearance.test.ts` read station data from `ships.json`, which has no mass/radius, and the plan's remedy is underspecified. A few test files outside `files_modified` take the new signature.

**Strengths**
- Keeping the names `stationDef`/`LaveFixture.stationDef` and only retyping them is genuinely good engineering: ~30 call sites compile unchanged, and the diff stays reviewable. The plan says so explicitly.
- The interim rule ("no app-level arrival test before 22.1-07") is an honest, testable constraint with a concrete grep guard, and it is repeated in 22.1-05 and 22.1-06 where it matters. This is the kind of cross-plan invariant most plans forget.
- `stationSpecFor` deriving `dockOffset` with the exact arithmetic `layout.ts` used (`Math.abs(position[2])`), and copying `(roll * Math.PI) / 2`, is how you preserve byte-identity. The behaviour list pins 500.2561, 779.3702392578125 and `(0.08 * Math.PI) / 2`.
- D-B is tested where it belongs: placement shell at 1.2 × radius (`src/sim/world/placement.ts:236-256`) and proximity at four radii (`src/sim/npc/proximity.ts:265-280`), per kind, with derived expectations rather than typed numbers.
- The frozen-file prohibition and the note that `thresholds.ts:313`'s comment goes stale (leave it, record it) show the plan understands what it must not touch.

**Concerns**
- **HIGH — the ships.json-based consumers have no viable data source in this plan.** `tools/ai-harness/populator-record.ts:200-212` caches `coriolis-station` from `ships.json` and `tests/sim/world/buoy-clearance.test.ts:58-69` uses `coriolis.shipDef`. `ships.json` entries carry no `mass`/`collisionRadius` (those live in `ships-client.json`), and both callers use `deriveSystemLayout`, which after this plan *requires* a `StationSpec`. The plan says "give them the spec of each system's own kind (the harness reads only the station position)", but does not say where the spec comes from in Node tests (a helper reading `ships-client.json`, i.e. `tests/helpers/stations.ts`, which is a test helper the harness cannot import). Either the harness must read `ships-client.json` directly or `stationSpecFor` must accept a catalogue-shaped input. This is a compile-level blocker that the plan papers over.
- **MEDIUM — `tests/helpers/stations.ts` has no caching requirement.** `stationSpecOf(kind)` will be called per system by the census (2,048) and per world by the launch corridor (40,960). `ships-client.json` is 19,644 B; re-reading and re-parsing per call is ~40k parses in a test that already takes ~91 s. `tests/helpers/dock-pose.ts` caches; `lave.ts` does not. The plan should say "cache the parsed catalogue once".
- **MEDIUM — the retype of `SessionCore.stationDef` to `StationSpec` drops the `ShipDef` fields other app code may still read.** `settings-controller.ts:202` guards undefined; `scene-manager.ts:42` uses it for the layout. Verified no other runtime use of `.shipDef` on `SessionCore.stationDef`, so this is probably safe — but the plan should assert it (a grep for `stationDef.` outside the layout) because a silent `undefined` at a later phase would be expensive.
- **LOW — the boot-order change is described but the failure path is thin.** "A `StationRecordError` goes to the existing boot failure surface" — fine, but the saved system is resolved *after* `loadSessionContent`; the plan should state that `stationSpecFor` runs after the saved system is known and before `scenes.enterSystem`, not merely "after the saved system is resolved".
- **LOW — `tests/content/player-ship.test.ts` is repurposed** ("move the no-dock assertions to `stationSpecFor`"), but `stationSpecFor` lives in `src/content/stations.ts` which imports nothing at runtime; the test currently reads `ships.json`. The plan does not say the test must switch data source to `ships-client.json`.
- **LOW — no mention of `src/app/session/probe-publisher`/probe shape**; that is 22.1-12's job, fine, but a `stationKind` probe field would be cheaper to add here while the spec is in hand.

**Suggestions**
- Decide and state the harness/Node-test data source: add `tests/helpers/stations.ts` for tests and let `tools/ai-harness/populator-record.ts` read `src/content/generated/ships-client.json` directly (it is a Node script, not app code), with `stationSpecFor` taking `readonly CatalogEntry[]` so both work.
- Add "cache the parsed catalogue in `tests/helpers/stations.ts`" and a note that the census/corridor helpers must not re-read per call.
- Add an assertion (or a grep check) that nothing outside `layout.ts`/`scene-manager.ts` reads fields of `ctx.core.stationDef` that `StationSpec` lacks.
- Specify `ships-client.json` as the data source for the moved `player-ship.test.ts` assertions.

**Risk Assessment**
**HIGH.** Not because the design is wrong — it is the right design — but because this plan is where four independent migrations meet (sim signature, app boot order, test helpers, AI harness), and one of them (the harness/buoy-clearance data source) is genuinely unresolved. Executed as written, it likely fails typecheck in `tools/ai-harness` and stalls.

## 22.1-05

**Summary**
Small, well-targeted, and correct in substance: move the blockage mass from a kind-keyed literal to the layout's `stationMass`, keep the sim's `StepOptions.stationMass` optional for the frozen detectors, add per-kind boundary trials, and record the superseded 2026-11-07 decision. **Strengths**
- Keeping the sim type optional *because the frozen detectors omit it* is exactly the kind of constraint that must be written down, and the plan writes it down twice (must-have and the prohibition).
- Making `StepOptionsInput.stationMass` required is the right way to prevent a silent "no blockage" regression: a missing mass becomes a compile error rather than a behaviour change.
- Per-kind trials at `r ± 1 m` and at the exact `0.1 * mass` boundary test the strict predicate (`src/sim/hyperspace/countdown.ts:110-119`) the way Oolite defines it.
- Recognising that `recorded-flights.ts`, `world-cadence.test.ts` and `ship-field.test.ts` can keep their hashes because the Coriolis mass is numerically identical is correct and reduces churn.
- The CHANGELOG entry is user-visible and phrased for a player.

**Concerns**
- **MEDIUM — FIDELITY row numbering is wrong.** The plan says "update rows 38 and 40 (and 45, 46 where they name the Coriolis as the only station with a mass)". Rows 45-46 are solid-subentity masses and station/buoy collision radius, not the blockage rule. Editing them to "per-station mass" would corrupt unrelated mechanics, and `tests/contract/fidelity.test.ts` resolves each Wegolite cell to a real line.
- **MEDIUM — the origin-vs-destination station is not called out.** The refusal message names the *blocker*, and a jump is blocked at the countdown completion against the **origin** station's mass (`isWitchspaceBlocked` is evaluated at the current position). The plan's test table uses "the layout of a real system of that kind" — fine — but the app wiring (`sim-driver` passes `layout.stationMass`) should be stated as "the live layout's mass, i.e. the origin system's". A future reader may otherwise wire it to the destination.
- **LOW — `tests/app/session/sim-driver.test.ts:1519` "change the non-Coriolis case to assert the Dodecahedron mass is supplied"** is right, but the test found that system by `station !== "coriolis"`, which happens to be a Dodecahedron today; the plan should say "a system whose `station` is `dodecahedron`" so the test does not silently start asserting an Icosahedron.
- **LOW — the deleted names are referenced in `tests/sim/world/ship-field.test.ts:27,438,590`, `world-cadence.test.ts:40,155`, `recorded-flights.ts:65,156`** — the plan lists them, good; but `CORIOLIS_STATION_MASS` may also be re-exported through a barrel. Worth a grep in the plan.
- **LOW — no test that a *nav buoy* still blocks with its own mass.** The change touches `StepOptionsInput`, so the buoy path (`countdown.ts:75,92`) deserves one unchanged-case assertion.

**Suggestions**
- Fix the row numbers: update only 38 and 40 (and 45 only if it literally claims "only the Coriolis has a mass"); leave 46 alone unless the radius text needs the per-kind note.
- Add "the mass supplied is the origin system's layout mass" to the sim-driver bullet and to one test name.
- Replace `station !== "coriolis"` with an explicit `"dodecahedron"` lookup.
- Add one buoy-blockage regression case to the per-kind table.

**Risk Assessment**
**LOW-MEDIUM.** The code change is small and the compile-error safety net is good. The risk is documentation damage (FIDELITY rows) and a mis-wired origin/destination mass, both cheap to prevent.

## 22.1-06

Good design intent — keep the frozen table, resolve the station key through the layout with two functions — and the per-kind dock/contact/twist tests are well chosen. Execution detail is where it strains: the plan's edit list omits two files it tells the executor to change, the `death.ts`/`ledger.ts` narrowing is a real signature question the plan hand-waves ("narrowing only where it reads the row"), and the acceptance's `rg -i "coriolis"` check will fail on legitimate comment lines unless the filter is precise.

- The buoy rows keep their own keys, so only the station row resolves through the layout — minimal blast radius.
- Per-kind twist assertions are derived from the port/ship boxes (`slotTwistedForShip`, `src/sim/dock/corridor.ts:137-142`), and the Dodecahedron "untwisted" consequence is a genuine, non-obvious finding from the dock extents.

- Keeping the dock-mouth oracle's Coriolis fixtures unchanged, and saying *why* (independent author; new fixtures would need a new author), is the right call.

**Concerns**

**Concerns**

- HIGH — The "every kind after the first in-flight frame" prefetch starts inside the measurement window of the first-load ceiling in two specs, and the headroom is smaller than the two GLBs. Facts:
  - `tests/e2e/budget.spec.ts:286-312, 386` sums `responseBodySize` of every same-origin request finished when `waitForMode(page, "inFlight")` returns; there is no path filter. Its header (`:33-37`) says the test relies on no prefetch running in this bundle "also ... in the frames after the first in-flight one".

  - Whether the bytes are counted depends on whether the fetches finish before the spec's next statement runs (one rendered frame plus one or two protocol round trips, on a software-GL container where a frame is slow). That is a race that will usually be lost by the test on at least one of the two specs.
  - Task 2 ends with `verify-full`, which runs both specs; neither spec is in this plan's `files_modified`, and plan 12 touches only `budget.spec.ts`.

The destination is already prefetched at the countdown start (15 s ahead) and a late model attaches without a throw, so the "all kinds" fetch only buys the first arrival at an unvisited kind on a slow link. It costs about 10 MB of download for every player who launches once, and three sets of decoded textures held for the session (per set roughly 11 megapixels, about 45 MB as RGBA) whether or not the player ever sees them. There is already a todo about texture memory (`2026-11-26-npc-atlas-texture-memory.md`).
- MEDIUM — A Continue at a non-Coriolis system downloads two stations. `preload()` still loads the default kind (`asset-cache.ts:167`) and the boot then awaits the saved system's kind, so such a first load is roughly 9 MiB plus 4 to 6 MB. - MEDIUM — Render settings for the Icosahedron are inferred from node names (see 22.1-10, second concern).
- LOW — A meshless `StationBody` must still provide `dock` (`bodies/station.ts:63-68`); the plan says "pose and roll but no mesh" and should name the placeholder.
- LOW — A prefetch in flight when the page reloads or the session is disposed produces aborted requests; specs that collect request failures or console errors may see them. The NPC prefetch has the same property, so the handling exists; mirror it.

**Suggestions**

- Drop the "every kind" background fetch. Keep: current kind awaited at boot, destination at the countdown start, late attach. That removes the HIGH entirely (no station request can occur before a countdown), the memory cost, and most of the bandwidth cost.
- If the owner wants the background fetch anyway: in this plan (not plan 12) change both specs the way `traffic.spec.ts` already treats NPC assets, that is, record the session mode at each fetch (`traffic.spec.ts:463-488`), assert that no station path was fetched in a mode other than `inFlight`, and subtract the station asset paths from both totals by path; add `tests/e2e/traffic.spec.ts` and `tests/e2e/budget.spec.ts` to `files_modified`; and record in `budgets.ts` that station prefetch is outside the ceiling, as D-07 does for NPC models. That is a change to what the ceiling measures and should be an owner-visible decision.
- For a Continue, load only the saved system's kind: resolve the saved system before `preload()` chooses its station.
- Read the layer per node from the record.

**Risk Assessment: HIGH** as written (the plan's own release gate is likely to fail or flake on a ceiling the roadmap names as implied work, and the fix is a design choice, not a typo). MEDIUM once the prefetch is dropped or the two specs are amended in this plan.
