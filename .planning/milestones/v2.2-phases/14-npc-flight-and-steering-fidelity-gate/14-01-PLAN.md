## Oracle fixture contract (shared with plan 14-02; identical text in both plans)

1. A fixture file is a JSON array of fixture objects. Plans 14-01 and 14-06 write `tests/oracles/npc/fixtures/<group>.json`; plan 14-02 writes `tests/oracles/npc/pursuit/fixtures/<group>.json`. Fixture ids are kebab-case and unique across both trees.
2. A fixture object has exactly these keys (strict): `id`; `title`; `oolite` (non-empty array of citations `<path>:<a>-<b>`, path starting `src/Core/` or `Resources/`, lines at commit `7437f22`); `derivation` (prose: how every expected value was obtained); `dt` (exactly 1/120; 1/60 is allowed only when the id starts with `rate-`); `horizon` (integer ticks, 1 to 36000); `stats` `{ maxFlightSpeed, maxFlightRoll, maxFlightPitch, thrust, mass, forwardWeapon, scannerRange }` with `forwardWeapon` one of `EQ_WEAPON_NONE`, `EQ_WEAPON_PULSE_LASER`, `EQ_WEAPON_BEAM_LASER`, `EQ_WEAPON_MINING_LASER`, `EQ_WEAPON_MILITARY_LASER`, and `scannerRange` Oolite's default 25600 (`SCANNER_MAX_RANGE`, `ShipEntity.m:553`; read at 8706, 4775 and 5038; the nine records never author `scanner_range`, plan 14-03 refuses it); `self` `{ id (always 101), scanClass, radius, position, forward, up, right, speed, flightRoll, flightPitch, stickRoll, stickPitch, accuracy (resolved, -5 to 10), frustration, successFactor, pitchingOver, jink, behaviour, targetId, destination, desiredRange, desiredSpeed, ownerId, escortSlot }`; `bodies` (array of `{ id, kind ("ship", "player", "station", "planet", "sun" or "buoy"), scanClass, radius, mass, position, forward, up, right, speed, behaviour, targetId }`; the player is id 100, statics 1 to 5, other ships 102 and up); `motion` (`"static"`, or `"constant-velocity"`: at the start of every tick each body advances along its own forward by `speed * dt` and never rotates); `assign` (ordered ShipControl calls applied at tick 0, each `{ op, value }` with op `setTarget`, `setDestination`, `setDesiredRange`, `setDesiredSpeed` or `perform`; may be empty); `draws` (unit draws in [0, 1) in Oolite's call order; the consumer fails when the port consumes a different number); `checks` (non-empty array of `{ tick, field, expected, tolerance, note }`, tick 0 to horizon, tick 0 meaning after `assign` and before the first update); `events` (the exact ordered list of `{ tick, name }` the steering posts, names from the closed list `shipAchievedDesiredRange`, `shipNowFacingDestination`, `shipAIFrustrated`, `shipTargetLost`; an event Oolite posts on every update while its condition holds, such as intercept's `shipAchievedDesiredRange` inside the desired range (`ShipEntity.m:3822-3825`), appears once per tick, so such fixtures keep the horizon short; an empty array asserts none). Only `self` is steered: a second steered ship, such as a second escort follower, is expressed as a separate fixture with its own `self`. Every ship uses Oolite's default `reaction_time` of 1.5 s (`ShipEntity.m:717`; plan 14-03 refuses an authored value).
3. Frame: every vector is in Oolite's world frame (a ship's forward is its local +Z; forward, up and right are unit, orthogonal within 1e-9, and right × up = forward). Wegolite's world is Oolite's with every z component negated (the content build's mirror); a consumer applies exactly that mapping and nothing else.
4. Tick semantics: tick k is the state after k native updates of self, each `processBehaviour:` followed by `applyAttitudeChanges:` and `applyThrust:` in the order of `ShipEntity.m:2485-2638`, with `delta_t = dt`. Inside one tick, in this order: (a) every body advances by its `motion`; (b) when `self.ownerId` names a body (the escort leader), self's destination is set from that body's pose and radius by the default escort pattern for `self.escortSlot` (the leader-refresh rule: Oolite updates the lower-id leader first and the leader writes each escort's destination after its own update, `ShipEntity.m:2427-2436`, `Resources/Scripts/oolite-global-prefix.js:165-193`); (c) self's native update; (d) the proximity rule: self's alert is cleared (`CollisionRegion.m:271`), then for every body whose kind is not `planet` or `sun`, in ascending id, the pair trigger (`dist² < PROXIMITY_WARN_DISTANCE2 × r²` for either collision radius, `CollisionRegion.m:304-312`, `Universe.h:99-100`) followed by `setProximityAlert:` for self with that body as `other` (`ShipEntity.m:6098-6146`, using the body's `mass`, `radius` and `kind`; self is crewed, is not a station and is neither launching nor docking); the alert set in (d) of tick k is read at tick k+1 (`Universe.m:6532-6609`, collisions after updates and think). Oolite visits pairs in collision-chain order (`CollisionRegion.m:286-312`), not by id; the ascending-id order is a recorded divergence that matters only when two alerts compete in one pass outside AVOID_COLLISION (inside it the subtended-angle rule of `ShipEntity.m:6133-6142` decides). Oolite also tests a pair only when its collision-chain prefilter chains the two entities (each entity's ±2 × collision-radius interval must overlap another collidable entity's on every axis, `Universe.m:6713-6760` and 7045-7073, `CollisionRegion.m:243-248`); rule (d) has no prefilter, a recorded divergence that never affects a pair of equal radii (the trigger implies the overlap) and is a no-op wherever a planet's ±2R interval contains both bodies (the planet collides, `Entity.m:825` and `OOPlanetEntity.m:120`, and Oolite places a main station 2R from its planet's centre, `Universe.m:1541-1547`), so a fixture whose alert depends on a pair of unequal radii either includes such a planet body or keeps both bodies' per-axis offsets below 2 × (r1 + r2) while the trigger holds. A `setTarget` in `assign` starts the reaction-time tracking curve at tick 0 exactly as `addTarget:` does (`ShipEntity.m:8659-8665`, `startTrackingCurve` at 5425-5442: four samples of the target's tick-0 position with times now, now − reactionTime/3, now − 2·reactionTime/3 and now − reactionTime). A check at tick 0 may only name fields that a `perform*` method sets without a draw, the ship's stats or another body (`behaviour`, `frustration`, `desiredSpeed` for STOP_STILL); the effects that need one of those (performTumble's sticks, performAttack's desired range, performFlee's jink and evasive choice, `ShipEntityAI.m:350-480`) are checked at tick 1 or later, and their draws come first in `draws`, before the draws of the first update's behaviour.
5. Fields (closed list, Oolite variable semantics): `flightSpeed`, `flightRoll`, `flightPitch`, `stickRoll`, `stickPitch`, `desiredSpeed`, `desiredRange`, `frustration`, `successFactor`, `pitchingOver` (0 or 1), `accuracy`, `behaviour` (a BEHAVIOUR name without the prefix; tolerance 0), `targetId`, `proximityAlert` (id; tolerance 0), `rangeToDestination` (centre distance), `rangeToTarget` (`rangeToPrimaryTarget`, `ShipEntity.m:9718-9733`), `headingErrorDestination`, `headingErrorTarget` (radians between self's forward and the direction to the destination or the target centre), `positionX|Y|Z`, `forwardX|Y|Z`, `upX|Y|Z`, `jinkX|Y|Z`, `destinationX|Y|Z`, `aimPointX|Y|Z` (`calculateTargetPosition`, `ShipEntity.m:5412-5423`) (Oolite frame).
6. Tolerances: every check states one. A simulated value's tolerance is at least four times the reference's measured |float32 − float64| difference at that check plus 1e-9; a closed form's tolerance is stated beside its derivation; discrete fields use 0. A pose whose threshold decision flips between float32 and float64 inside the horizon is moved away from the threshold, never covered by a wider tolerance (this applies to continuous quantities such as ranges; time accumulators follow item 8).
7. Random draw rule: each Oolite `randf()` consumes one unit draw u; each `ranrot_rand() % N` consumes one draw and yields `floor(u * N)`.
8. Accumulators and the clock: `frustration` and `success_factor` are GLfloat in Oolite (`ShipEntity.h:337`), so every `+= delta_t`, `-= 0.25 * delta_t` or assignment rounds the double result to float32, and a time threshold is crossed later than a float64 sum crosses it (planner's computation by fround accumulation from 0: `frustration > 0.5` first holds at tick 61, not 60; `> 7.5` at 901, not 900; `> 9.375` (15 / 1.6) at 1126, not 1125; `> 10.0` at 1201, not 1200; `> 12.5` at 1501 and `> 15.0` at 1801 in both widths). The contract fixes one rule: every write to `frustration` and `successFactor` is `Math.fround(value)`, in the reference (in both its float32 and float64 modes, so the float32-versus-float64 measurement of item 6 concerns continuous values only) and in the port; an event or check at an accumulator threshold is therefore exact (tolerance 0, no plus-or-minus-one-tick rule), and every such tick is derived by fround accumulation in a loop, never as `ceil(seconds × 120)`; the oracle author recomputes each tick it uses. `desiredRange`, `desiredSpeed` and the other GLfloat fields are not emulated by the port; a decision that would flip on their float32 rounding is avoided by item 6. The clock is the integer tick: at tick k Oolite's `[UNIVERSE getTime]` is read as k ticks, and a stored-time compare such as the tracking-curve gate `trackingCurveTimes[0] + reactionTime / 3.0 > now` (`ShipEntity.m:5448`) is the whole-tick compare `ticks[0] + 60 > k`. Oolite's own `universal_time` is a double sum of `delta_t` (`Universe.m:6456`): from a base of 0 the gate opens at tick 60, from a base of 1000.0 at tick 61, so the 60-tick rule is a recorded divergence of the frame-rate rule (plan 14-06 records the measured one-tick difference), and an `aimPoint` check at a sampling tick tests the rule, not a base-dependent tick.
