Deferred model requests (owner decision 2026-11-14, option A; DATA-13 and ROADMAP Phase 9 criterion 3 unchanged, no ceiling change):
- The problem: traffic is on in production, `launched` is emitted at launch start (src/sim/flight/step.ts line 126) and plan 12-08's `begin` populates the 12 ships there, so a driver that requested models on first appearance would fetch GLBs during the launch frames, before the first in-flight frame. The NPC assets total 12,348,793 bytes (nine GLBs, 820,068; 43 textures, 11,528,725) against a cold-start baseline of 8,835,212 bytes (docs/PERFORMANCE.md line 41) and the unchanged ceiling of 9,437,184 (headroom 601,972).
- The condition: an NPC model may be requested only after the first in-flight frame has been presented. Its source is this plan's render driver, `renderFrame` in src/app/session/render-driver.ts: a call with `draw` true in which `currentState.mode` is `inFlight` and `renderer.render(currentScene.scene, currentScene.camera)` has returned. That same call ends with `updateProbe()`, which publishes `probe.mode = "inFlight"` (src/app/session/probe-publisher.ts line 266), the signal `waitForMode(page, "inFlight")` of tests/e2e/budget.spec.ts calls the first in-flight frame.
- The mechanism: `NpcModelLoader.open()`, a one-way latch on the per-session loader. Before it, `request(keys)` does nothing and remembers nothing. The driver calls `request` with the frame's contact keys before rendering, every frame, and calls `open()` right after `renderer.render` in a frame whose state is `inFlight`. The first fetch therefore starts in a later `renderFrame` call, after the first in-flight frame was drawn, published and handed to the browser to present. The frame loop calls `renderFrame` once per animation frame (src/app/session/frame-loop.ts line 157; its chart and save-screen branches return before it), so this is normally the next animation frame.
- Lifetime: one loader per session, created and disposed by src/app/game-session.ts; the latch never closes, so a later dock, launch, Load or jump in the same page requests at once (DATA-13 concerns the cold start); a Continue into an in-flight save opens it after its first drawn frame.
- Compatibility: Open Question 5 holds unchanged after the latch (per key, on first appearance in the contact list, draw only loaded keys, a failed key is never retried, the scanner still shows the ship); a traffic-off session has no contacts, so `open()` changes nothing for it; tests/e2e/budget.spec.ts and tests/e2e/npc-assets.spec.ts stay unchanged (the first runs traffic off; the second fetches the GLBs directly from a plain session).

Pattern analogs (12-PATTERNS.md, "src/render/bodies/npc-ships.ts (new NpcLayer) (WORLD-15)"): npc-ships.ts follows the scene-owned bodies src/render/bodies/buoy.ts (lines 1-60: imports `three`, the `GLTF` type and `isMesh, meshMaterials` from `../mesh.js`; disposes only what it owns) and src/render/bodies/ship.ts (the player model path; the NPC layer must not clone materials as ship.ts does); PATTERNS lists the instancing itself under "No Analog Found" (no InstancedMesh in src/render), so it follows RESEARCH Pattern 5. src/app/npc-models.ts has no PATTERNS row; its closest analog is the memoised, path-checked `loadNpcModel` of src/render/asset-cache.ts and its test doubles in tests/app/asset-cache-npc.test.ts.
