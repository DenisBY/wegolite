# Stack Research

**Domain:** Browser port of Oolite, v2.3 "Combat and Death" (NPC laser fire, station/buoy hits, ship destruction with wreckage and cargo, ship collisions, player death)
**Milestone type:** Subsequent. The v1/v2.0-v2.2 stack is validated and not re-researched.
**Researched:** 2026-11-16
**Confidence:** HIGH (every numeric claim is read from the Oolite checkout at `/home/opencode/git/oolite`, every integration claim from the current Wegolite tree; versions checked against the npm registry and Context7)

## Verdict

**Add zero runtime dependencies. Add zero dev dependencies. Do not change the Docker image. Do not bump any pinned version.**

Every v2.3 capability is covered by the existing stack plus arithmetic that Oolite already specifies. The work is in four places, none of which is a package:

| New capability | Answer | New package |
|----------------|--------|-------------|
| NPC laser fire, NPC-vs-NPC hits, shield/energy damage | Hand-written sim code in `src/sim/combat/` and `src/sim/npc/`, reusing the existing `isHitByLine` octree test, `shields.ts` and the `weapon_info` numbers already in `equipment.json` | none |
| Lasers/ident hitting the Coriolis and buoys | Extend the build-time hull catalogue with two more hulls (generated by the existing `tools/oolite-ingest` octree builder) | none |
| Wreckage, alloy plates, cargo pods, entity cap | Hand-written sim rule (`becomeExplosion`, `releaseCargoPodsDebris`) plus 8 more vendored Oolite model files run through the existing GLB/octree/texture pipeline | none |
| Ship-ship / ship-buoy collision damage | Port `Octree.m` `isHitByOctree` (hull vs hull) next to the existing `isHitByLine`; damage is one closed-form expression | none |
| Internal-hit equipment damage (CBT-08) | Hand-written; `damage_probability` is already compiled into `equipment.json` | none |
| Player death, game over, load last save | Existing `persistence/` + `session/` controllers; one new state edge, no storage change beyond a possible save-schema bump | none |
| Explosion, flash, hull-spark, debris drawing | `THREE.InstancedMesh` / `THREE.Points` pools in `src/render/bodies/`, same pattern as `laser-shots.ts` and `npc-ships.ts` | none |

The decisions that look attractive and are rejected are listed under "What NOT to Use".

## What the Oolite source requires numerically

All values are read from `/home/opencode/git/oolite/src/Core/` and verified against the vendored `third_party/oolite/Config/`. Each row is the number the sim must reproduce; none needs a library.

### Collision damage (`ShipEntity.m` `collideWithShip:`, 11020-11171)

| Quantity | Rule | Source |
|----------|------|--------|
| Closing speed along line of centres | `v2b = dot(v_self - v_other, loc)`, `loc` = unit vector self to other | 11060-11072 |
| Moving apart | `v2b < -1` returns with no effect; `-1 <= v2b < 0` is treated as 1 m/s | 11076-11083 |
| Damage to self | `dam1 = m_other * v2b^2 / 50_000_000` | 11087 |
| Damage to other | `dam2 = m_self * v2b^2 / 50_000_000` | 11088 |
| Threshold | scrape damage applies only if `dam > 0.05` | 11106, 11115 |
| Station | `otherDestroyed` is false and the station is never moved | 11097, 11134 |
| Velocity exchange | `v1a = sqrt(v2b^2 * m2 / m1)`, applied along `loc` | 11062-11066 |
| Fragment chance on a lethal scrape | `frag_chance = other.mass * 10 / self.mass`; `randf() < frag_chance` sets `being_mined` | `takeScrapeDamage:` 11659-11666 |

Mass is already computed at build time (v2.1 DATA-11) for every NPC hull, the Cobra, the Coriolis and both buoys, so the rule needs no new data.

### Hull-vs-hull test (`Octree.m` `isHitByOctree`, `ShipEntity.m` `doOctreesCollide`, 1879-1942)

Wegolite's `src/sim/combat/octree.ts` exports `isHitByLine` only. `isHitByOctree(axialDetails, otherDetails, delta, other_ijk)` (`Octree.m:76`) is **not** ported. It must be, as sim code next to `isHitByLine` and fuzz-tested against a brute-force triangle-vs-triangle reference with fast-check. Notes from `doOctreesCollide`:

- It first tests hull against hull, then each side's subentity hulls. A faithful first cut can ignore subentity hulls only if `FIDELITY.md` records the divergence.
- `canCollide` is false for wreckage (`ShipEntity.m:1865`: "wreckage won't collide"), for dead ships and for cockpit-display status. Wreckage therefore needs **no octree**; pods and alloy plates do.

### Destruction (`ShipEntity.m` `becomeExplosion`, 7891-8139, and `releaseCargoPodsDebris`, 7814-7879)

| Quantity | Rule | Source |
|----------|------|--------|
| Entity universe size | `UNIVERSE_MAX_ENTITIES = 2048` | `OOTypes.h:168` |
| Debris allowed | `n_entities < 0.95 * 2048` and frame time `< 0.125 s` (the second condition is a render-rate guard; the sim must use a deterministic substitute, see PITFALLS) | 7939 |
| Wreckage allowed | `n_entities < 0.50 * 2048` | 8047 |
| Alloy plate count | `n_alloys = (mass / 6000)^(1/4)`; then `n_alloys = randf() * n_alloys` after wreckage; `floor` it; `fragment_chance` false gives 0; near the cap at most 1 | 7916, 8068-8081 |
| Wreckage pieces | `n_alloys < 3 ? floor(randf() * (n_alloys + 2)) : 3`; sub-wreckage `(mass > 600 && randf() < 0.2) ? 2 : 0` | 8050-8057 |
| Wreckage scale | `expected_mass = 0.1 * ship.mass * (0.75 + 0.5 * randf())`; scale factor = cube root of `expected_mass / wreck_mass` | `Universe.m:5497-5509` |
| Wreckage life | `energy = lifetime`, `lifetime = (750 * randf() + 250 * i + 100) / 2`; burns at 1000 energy per second, so it vanishes at that age | 8063-8064, `Universe.m:5516-5518` |
| Cargo survival | `cargo_chance` starts 70 percent; after each survivor it drops by 30 (NPC) or 20 (player) down to 10; a hard `limit = 15` pods | `releaseCargoPodsDebris` 7823-7876 |
| Pod contents | 50 percent a commodity-role pod (none exist in vanilla, so effectively the generic `cargopod`), else `cargopod`; amount from `getRandomAmountOfCommodity` by the commodity's mass unit | `Universe.m:3860-3877`, 3977 |
| Debris position / velocity | random point in the bounding box plus `(ranrot % 7) - 3` per axis; velocity `0.1 * ((ranrot % 200) - 100)` per axis plus the ship's | 7847-7859 |
| Blast momentum | `dealMomentumWithinDesiredRange(0.125 * mass)` with `desired_range = 2.5 * collision_radius`; no energy damage to neighbours | 8124-8125, 7680-7711 |
| Cargo carried at spawn | `likely_cargo * (0.5 + randf())`, capped at the free cargo space and 200; contents by `cargo_flag` (plentiful 66 percent / scarce for traders, pirate flag for pirates) | `setCargoFlag:` 7323-7372; `Universe.m` 2538-2676 |

The cargo and wreckage numbers are independent of the entity cap; only the two thresholds use it. Wegolite's cap is `MAX_ENTITIES = 256` (`src/sim/world/ids.ts:53`), not 2048, so the thresholds are `0.95 * cap` and `0.50 * cap`. That scaling is a roadmap decision (see Open Questions).

### NPC laser fire (`ShipEntity.m` `fireLaserShotInDirection:`, 10360-10466; `setWeaponDataFromType:`, 6461)

| Quantity | Rule | Source |
|----------|------|--------|
| Per-weapon numbers | `range`, `energy`, `damage`, `recharge_rate`, `shot_temperature` from `weapon_info` | `equipment.plist` 131-160; already in `equipment.json` `conditions.weapon_info` and pinned by `tests/sim/combat/constants.test.ts` |
| Multi-barrel split | `effective_damage = damage / barrels` unless `_multiplyWeapons` | 10373-10376 |
| Hit test | first ship hit by the laser, then `hit_at_range^2 < range^2` | 10392, 10419 |
| Miss with a plausible aim | if `dot(shot_dir, normal(to_target)) > 0.995`, the target is told `ATTACKER_MISSED` | 10436-10447 |
| NPC fire loop gating | `fireWeapon:direction:range:` checks `shot_time`, temperature and `weapon_energy_use` | 10009-10100 (the AI ready checks use `COMBAT_AI_WEAPON_TEMP_READY` / `_USABLE`) |
| NPC energy damage | `energy -= amount`; `energy <= 0` calls `getDestroyedBy`; NPCs have no shields | `takeEnergyDamage:` 11418-11598 |
| Player energy damage | shields absorb first; remainder to energy; internal damage roll per 32 points | `PlayerEntity.m` 5640-5700 (already ported in `shields.ts` in v2.2) |

The per-ship weapon facings are **not yet compiled**. The current `NpcShipSchema` carries `forwardWeapon` and one mount position only. The nine ships need `weapon_facings` (moray is 15, the others 0-3), the aft, port and starboard weapon types and mount positions, `likely_cargo`, `max_cargo`, `cargo_carried`, `fragment_chance`, `heat_insulation` (only if heat is in scope, which it is not) and `explosion_type`. See "Content pipeline changes".

### Equipment damage (`PlayerEntity.m` `takeInternalDamage`, 6097-6182; `PLAYER_INTERNAL_DAMAGE_FACTOR = 31`, `PlayerEntity.h:331`)

| Quantity | Rule |
|----------|------|
| Roll count | `while (amount > 0) { if ((ranrot & 31) < amount) takeInternalDamage; amount -= 32 }`, for energy damage that does not kill and for scrape damage after shields |
| Considered slots | `n_considered = (max_cargo + mass/10000) * ship_trade_in_factor / 100`; `damage_to = ranrot % n_considered` |
| Cargo first | if `damage_to < cargo.count`, that pod is destroyed |
| Equipment next | the slot indexes the list of damageable equipment; the item is chosen by `damage_probability` weights (default 1.0, 0 for missiles, mines and 7 listed items); the item becomes `<KEY>_DAMAGED` |
| Cosmetic | `(damage_to & 7) == 7 && trade_in_factor > 75` lowers `ship_trade_in_factor` by 1 |

`damage_probability` is already in `src/content/generated/equipment.json` (seven explicit zeros; the others default to 1.0 per `OOEquipmentType.m:247`). The ingest needs no change for this. **The save needs a way to hold a damaged item and `ship_trade_in_factor`**: see Integration Points.

### Player death (`PlayerEntity.m` `getDestroyedBy:`, 6184-6218)

No numbers beyond `becomeLargeExplosion:4.0`. The flow is: ignore if docked, set energy 0, disengage autopilot, explode, show game over, remove all equipment. Wegolite replaces "show game over" with its own screen and "reload `save_path`" with the existing load of the last save.

## Content pipeline changes (the real stack work)

These are changes to `tools/oolite-ingest/`, `scripts/vendor-oolite.sh` and the schemas. They use only what the repo already has.

### 1. Vendor eight more files (via `scripts/vendor-oolite.sh` only)

| File (under `Resources/`) | Why | Notes |
|---------------------------|-----|-------|
| `Models/wreck1.dat` ... `wreck5.dat` | the `wreckage` role models (`oolite_template_wreckage-component` and the `more-wreckage2..5` variants, `shipdata.plist` 4227-4600) | Not named `oolite_*`; they use texture `wreck.png`. The `NpcShipSchema.model` regex `^oolite_[a-z0-9_]+\.dat$` and `NPC_GLB_PATH_PATTERN` reject them: the debris records need their own schema or a widened regex |
| `Models/oolite_alloy.dat` | `alloy` role, the scrap plates | material `oolite_alloy_diffuse.png`, emission map from the alpha channel |
| `Models/oolite_barrel.dat` | `cargopod` role (`oolite_template_barrel`) | 300 vertices, 156 faces; textures `oolite_barrel_diffuse/normal/specular.png` |
| `Textures/wreck.png`, `oolite_alloy_diffuse.png`, `oolite_barrel_diffuse.png`, `oolite_barrel_normal.png`, `oolite_barrel_specular.png` | those models' materials | add to `VENDORED_TEXTURES` in `convert/textures.ts`; the explicit-list rule means a texture is vendorable only if an emitted material references it |
| `Textures/oolite-particle-cloud2.png`, `oolite-particle-fragments.png`, `oolite-particle-fragments2.png`, `oolite-particle-cloud.png`, `oolite-particle-flash.png` | explosion cloud, fragment, flash and spark sprites (`explosions.plist`, already vendored) | a new asset class: particle sprites, not ship materials. Add a small separate list and a provenance row each |

Each file also needs an `ASSETS.md` row (the script errors if a vendored path has none). These are CC BY-NC-SA 3.0 like every other Oolite art file, which fits the project licence note. `escape_capsule`, `boulder`, `splinter`, `asteroid` and `thargon` models are **not** needed (escape pod, mining and scooping are out).

### 2. Widen the NPC record

`src/content/schemas/ship-npc.ts` and `tools/oolite-ingest/convert/npc-ships.ts` add, per ship: `weaponFacings` (bit mask), `aftWeapon`, `portWeapon`, `starboardWeapon` and their three mount positions, `likelyCargo`, `maxCargo`, `cargoCarried`, `fragmentChance`, `explosionType`. Values for the nine ships are listed in `shipdata.plist` (`oolite_template_*`), with `like_ship` already resolved by `tools/oolite-ingest/like-ship.ts`. Because the schema is `z.strictObject`, the build and the loader must change together, and the drift check (`assets:check`) will show the diff.

Spot values the ingest should reproduce (read from `shipdata.plist`): adder likely/max cargo 2/5, facings 1; cobramk1 10/10, facings 3; gecko 3/3; krait 2/2; mamba 3/4; moray 5/7, facings 15; shuttle max 30; sidewinder none; viper none and `has_escape_pod` (ignored, escape pod is out).

### 3. Hull catalogue: add the Coriolis, the buoy, the pod and the alloy plate

`ships-hulls.json` today holds the Cobra and the nine NPC hulls (10 hulls, 89,673 bytes). Adding the Coriolis and the buoy (for CBT stations/buoys), the barrel and the alloy plate (for collisions; wreckage needs none) gives 14. The loader's bounds are the concern:

| Bound (`src/content/schemas/ship-hull.ts`) | Current | Risk |
|--------------------------------------------|---------|------|
| `MAX_HULLS` | 16 | 14 fits; no room for later asteroid, boulder, splinter, escape capsule, so raise to 32 now |
| `MAX_HULL_NODES` | 16,384 | A depth-7 Coriolis octree can approach or exceed this. **Measure it in the `assets` container before committing to a number** |
| `MAX_HULL_ARTIFACT_BYTES` | 200,000 | The file is already 89,673 bytes; the Coriolis alone may take it past the cap |

Recommendation: put the Coriolis and the buoy in a **separate generated file** (`ships-statics-hulls.json` or similar) with its own cap, loaded by the same lazy-glob loader, so the NPC chunk keeps its size and the station hull can be required in every session (it is on screen in every session; the NPC catalogue is traffic-only). Measure first; if the Coriolis octree is small, one file is fine. The ingest already builds the Coriolis octree for its mass (`ship-mass.ts`), so no new builder is needed.

### 4. Explosion data

`explosions.plist` is vendored but not compiled. Compile the eight entries v2.3 uses (`oolite-default-ship-explosion`, `oolite-wreckage-explosion`, `oolite-fragment-explosion`, `-b`, `oolite-hull-spark`, `-b`, `oolite-wreckage-chunk` plus `-explosion`, `oolite-default-asteroid-explosion` only if asteroids come back) into a small `explosions.json` (count, duration, growth_rate, size, alpha, color_order, spread, texture). The renderer reads it; the sim never does (it is pure presentation).

## Alternatives Considered

| Recommended | Alternative | When to Use the Alternative |
|-------------|-------------|------------------------------|
| Hand-written damage and destruction rules | A physics engine (Rapier, cannon-es, ammo.js) | Never here. Oolite's collision is a closed-form energy rule on octrees, not rigid-body dynamics; a physics engine would break determinism, the world hash and the "faithful numbers" goal |
| `InstancedMesh` / `Points` pools | `three.quarks`, `three-nebula`, `three.proton` particle libraries | If the project ever wants non-Oolite effects. Oolite's explosion is a count of billboarded sprites with a growth rate, which is under 100 lines in the existing pool pattern |
| Port `isHitByOctree` | `three-mesh-bvh` | Never: it works on triangle meshes at render time, is not deterministic with Oolite's octree results, and the sim may not import Three |
| Plain functions over `World` | An ECS or state-machine library (bitECS, XState) | Never here: v2.0 already chose a hand-rolled `EntityStore`; XState would hide the AI/death transitions that the world hash must see |
| Existing IndexedDB save + schema bump | A new store for "death records" | Only if a later milestone adds a high-score or obituary list; v2.3 stores nothing on death |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| Any physics or collision library | Non-deterministic against the Oolite rule, would put a second collision model beside the octree one | `isHitByOctree` plus the `m * v^2 / 50_000_000` expression |
| A particle-system package | Extra bundle weight and a second timing model; explosions are presentation only | A fixed pool in `src/render/bodies/` driven by `explosions.json` |
| Running `explosions.plist` or `shipdata.plist` at runtime | Build-time compilation is the project rule | Compile to generated JSON through the ingest |
| Raising `MAX_ENTITIES` to Oolite's 2048 by reflex | `proximity.ts` and the NPC step walk the live set; the cost rises with the square for pair work and the acceptance run is frozen at the current cap | Scale the 0.95 and 0.50 thresholds to the current cap, decide a cap change separately with a measurement |
| `Math.random()` or `Date.now()` for debris | Breaks replay hashes and the 20-seed acceptance run | The per-entity seeded streams in `src/sim/rng.ts` |
| Frame-time-dependent debris gating (`getTimeDelta < 0.125`) | Oolite's guard reads wall-clock frame time, which a deterministic fixed-step sim cannot | Gate on entity count and a sim-time budget only; record the divergence in `FIDELITY.md` |
| A server or database for death/game-over | Out of scope by the no-database rule | Load the last IndexedDB save |
| Upgrading TypeScript to 7, Vite to 8.3.8, Vitest to 5.1, Playwright to 1.65 mid-milestone | Latest published versions are newer than the pins (checked 2026-11-16), but a toolchain bump is unrelated to this milestone and the Playwright image pairs with the Playwright version | Keep the pins; bump in a separate chore |
| Audio, escape-capsule and boulder/splinter/asteroid assets | Explicitly out of the milestone | Leave them in the backlog |

## Stack Patterns by Variant

**If the Coriolis octree fits the existing hull caps** (measured in the `assets` container):
- Keep one `ships-hulls.json` and add the Coriolis and buoy to it, raising `MAX_HULLS` to 32.
- Because it removes a second loader and a second schema.

**If it does not fit:**
- Generate a separate statics hull file and load it with the world, outside the traffic-only NPC chunk.
- Because the station is in every session and the NPC chunk must stay lazy (DATA-13).

**If the owner wants damaged equipment to persist across a save/load:**
- Bump to save schema v5 with a `damagedEquipment` list and `shipTradeInFactor` (default 100), ordered migration from v4.
- Because the Oolite rule changes `_DAMAGED` keys the player sees at the equipment screen; losing them on load would be an unrecorded divergence.

**If the owner keeps the save at v4:**
- Make damage session-only and add a `FIDELITY.md` row; the load-last-save death path then restores undamaged equipment, which is also what a reload in Oolite does after death.
